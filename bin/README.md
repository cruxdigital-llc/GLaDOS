# Binaries

This directory contains the GLaDOS v2 toolchain.

## `glados.py`

The compiler, type-checker, and installer — one file, standard library only
(Python 3.10+). It replaces the v1 `glados-install.sh` / `glados-update.sh`
scripts; the update flow is simply re-running install.

It reads `glados.yaml` and the preset table with its own YAML subset. What
the subset accepts, it reads as a YAML reader (and so the agent) does;
anything else, such as an anchor, alias, tag or merge key, a key YAML reads
as a null, bool, number or date, or a line indented less than a block
scalar's text but more than its key, is an error naming the file and line.

**Subcommands** (see `python bin/glados.py --help`):

| Command | Does |
|---|---|
| `install` | Compile the sources against the target's `glados.yaml` and emit one adapter (`--mode claude \| claude-plugin \| direct \| gemini \| antigravity \| aistudio \| pi`). Warns, without failing, about unknown top-level `glados.yaml` keys and `params:` keys nothing reads. In every mode but `claude-plugin` it adds the project's run-record line to the clone's git exclude file (`/.glados/runs/*`, or `/<dir>/.glados/runs/*` for a project in a subdirectory of its repository), saying so when it adds it. |
| `check` | CI mode: recompute the compile and diff it against the installed files; drift, failed type checks, or a stale manifest hash fail the job. The hash covers only the structural keys (`phase`, `optimize-for`, `default-modules`, `workflows`, `disabled-workflows`, `sda`, and each pipeline's name and description), so editing a live key such as `channels` or `params` never makes the compile stale; the type checks still run on those values, so an invalid one (an undeclared sink, an unconfessed relaxation, a misspelt decision class or merge authority, a loop bound that is not a whole number of 1 or more) fails it. Warns, without failing, about unknown top-level keys and `params:` keys nothing reads. |
| `validate` | Type-check the target's `glados.yaml` in memory, its `pipelines:`, `steps:` and `canon:` included (step bodies in `product-knowledge/steps/` too, and whether each canon digest exists): every check `install` runs, with errors and warnings printed. Writes nothing, needs no install (a plugin-only repo runs it from the plugin's own `bin/glados.py`), exits 1 on any error. `run-pipeline` runs it before its first step. |
| `effective-config` | Print the digest of the configuration a run obeys: the target's `glados.yaml` layered over the preset table (`.glados/presets.yaml`, else this toolchain's own), so the bounds and decision rights a manifest inherits are in it. `run-pipeline` pins it beside the blob hashes of `glados.yaml` and its step bodies; `--ref <commit>` reads `glados.yaml` as that commit has it, and the preset table too when the commit tracks one (else the table the working tree reads), for a resumed run. Exits 1 with no digest, which `run-pipeline` treats as an escalation and a stop, on a loop bound that is not a whole number of 1 or more, on one a workflow it enables references that the table leaves absent or null, on a decision class or merge authority the table misspells, and on a table out of shape. When another GLaDOS version built the install (before the reinstall of an upgrade), its first line says so: the table is that version's, and what it lacks is the reinstall's to supply, not `glados.yaml`'s. |
| `doctor` | Staleness + wiring report (never fails): the installed modes, the manifest hash, the vendored assembly report, whether the CI check and run-record hooks are wired (for a project in a subdirectory of its repository, "CI check wired: not supported": CI enforcement is supported only for a project at the repository root, and `install` prints no enable stanza for it), CODEOWNERS on `glados.yaml` (and on `product-knowledge/steps/` and `product-knowledge/canon/` once the project uses them), the phase, unknown top-level keys, confessions, SDA artifacts and canon digests. |
| `migrate` | Guided v1 to v2 migration: detect v1 layouts, generate `glados.yaml` (phase left for a human), convert `specs/` history to run records in `.glados/runs/` (kept out of commits by the line it adds to the clone's git exclude file; save them to the `glados/ledger` branch with `ledger save` after install). Non-destructive by default; `--dry-run` writes nothing, `--clean` removes the converted `specs/` dirs and the detected v1 command layouts. |
| `verify-ledger` | Scan git history for silent-loss candidates, and list any run record a branch commits since its base: `--base <target branch>`, or in CI the merge request's diff base (`CI_MERGE_REQUEST_DIFF_BASE_SHA`) or the pull request's base (`origin/$GITHUB_BASE_REF`). Report-only: it never fails, and says so when the `glados/ledger` branch is not in the clone. |
| `ledger` | `save [paths]` commits run records from `.glados/runs/` onto the `glados/ledger` branch without touching the checked-out branch, the index or tracked files, merges what another session pushed, and pushes. With no paths it saves every file the ledger lacks or holds older; a named path that no longer exists is removed from the ledger (one this user cannot read stays on it, with a note), and a file or directory under `.glados/runs/` it cannot look at or list is named in a note as not saved. On Windows it reaches a file whose full path is 260 characters or more with long paths off, Windows' default (its `\\?\` form, and git with `core.longpaths`). It saves regular files only: a link or a Windows junction under `.glados/runs/` is neither saved nor walked into, and a file whose name the ledger holds as a directory, or one in a directory whose name the ledger holds as a file, is left off with a note, the ledger's copy kept. So is a repository kept among a run's files: git holds no path with a `.git` component, so save leaves those off with one note (keep the repository as an archive instead), as it does, on Windows, a name that is not valid Unicode. A local copy that is an earlier version of the ledger's is refreshed from it; one save cannot write (read-only) is left as it was, with a note, and the rest is saved and pushed. When this clone's ledger and the remote's both hold one name, one as a file and one as a directory, it does not merge them: it commits locally, pushes nothing, exits 1 and names both paths, until the clone's copy is renamed (`save --no-push <old> <new>`, then `save`). `--no-push` commits locally only; a failed push exits 1 and keeps the commit, which the next save pushes. It refuses while `glados/ledger` is checked out, and names the way out: remove a linked worktree, or switch the main working tree to another branch. `restore [names]` fetches the ledger and copies every record, or the named ones with their step artifacts, into `.glados/runs/`, never over a local copy with changes the ledger lacks or a file the branch tracks, and never where a directory or a file here takes the name (it names the path instead). It removes a copy it synced that the ledger no longer has (steward compacted it elsewhere) only when a ledger this clone reads held it once, and names one it cannot delete. On Windows it also leaves on the ledger, with a note, a file whose name Windows cannot hold (one with `? * : " < > |` or ending in a period, or a device name such as `aux`), which a clone on Linux or macOS can save; Windows and macOS do the same for a name that is not UTF-8, which Linux can save, and any platform for a name too long for its file system. `save` keeps such a file on the ledger on every platform. `link <paths>` prints each path's web link on the ledger. `save` and `restore` add the project's line to the clone's git exclude file, as install does, whatever encoding the file is in (one this user cannot write is named on stderr). Each works on the `.glados/runs/` of the project `--target` is in (the nearest directory up to the repository's top level with `glados.yaml` or `.glados/`), so a project in a subdirectory keeps its records under that subdirectory's path on the ledger. |
| `compile-plugin` | Shorthand for `install --mode claude-plugin --target <repo>`. |

**Usage**:

```bash
python bin/glados.py install --mode <mode> --target <dir> [--source <glados repo>]
```

The self-test suite lives at `tests/run_tests.py`.
