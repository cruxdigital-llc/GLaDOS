# Healthier, not just smaller

> Design rationale for the third round of 2.5 changes to run-pipeline and
> the fresh reviewers around it. The rules are in
> `src/vocabulary/review-inputs.md`, `src/vocabulary/questions.md`,
> `src/workflows/run-pipeline.md` (step 3 and **Branch**, **Commits**,
> **Bound** and **Questions** in step 4), `src/vocabulary/design-review.md`,
> `src/vocabulary/loop-bounds.md`, `src/workflows/implement-feature.md`,
> `src/modules/evaluator-spawn.md`, `src/modules/mr-review-panel.md` and
> `src/vocabulary/git-conventions.md`.
> Follows [design-loop.md](design-loop.md) and
> [review-inputs.md](review-inputs.md).

**Status:** part of 2.5.0, still a release candidate. **Baseline:** the
2.5.0 candidate with *Questions for a person* and the cycle table.

## The problem

The objective is a healthier change: every outcome the ticket and the
person ask for met robustly, with a structure the next caller can build on,
leaving the code it touches better. Plainness is a constraint on how it gets
there, not the goal. Three trial runs of a plain-first project pipeline on
one ticket, and a blind comparison of the third run's change with two other
implementations of the same ticket, showed the 2.5 loop drifting toward the
smallest change instead.

- **Outcomes were checked in the author's words.** The gates verified the
  author's restated outcomes and passed. Blind reviewers read the ticket's
  own words and found two of its four outcomes only partly met. Nothing in
  core stopped an author's "deferred" or "not met" from excusing an outcome
  the ticket asked for.
- **An answer was not carried out.** A person chose a reading that asked for
  certain cases to be reported; the change never reported them, and no gate
  asked where the answer was implemented or tested.
- **A repeated advisory never bound.** Three independent checks raised the
  same missing clean-up of stored rows as advisory; the author declined it
  each time, and the blind reviewers found it again.
- **The loop still turned on numbers.** A stalled-cycle bound of 3 was
  arbitrary, and a cycle that patched one path of a recurring class counted
  as progress. Narrow failure-path variants each parked the whole run for a
  person, because any reading that changed a unit or a failure path was
  "material".
- **Hedged words were read as hard requirements.** "I think I'd like…"
  cost one run three failed design reviews, and a later gate blocked twice
  on the detail of an option's wording that the person had only assented
  to.
- **Process weight.** The run record reached 182 KB and every agent read it
  whole. Each fix loop ran the full suite twice (implement-feature's step 5
  and the evaluator), about an hour each on the trial machine. The run made
  25 process commits beside 6 product commits, 6 of them for briefs alone.

## Why core, not project

A project chooses its steps, gates, checkpoints and the numbers in
`params.pipeline`, and its step bodies say what each gate checks. It cannot
change what a fresh reviewer is given or told a deferral excuses (that
fragment is compiled into the evaluator, the MR panel and every design
review), what the evaluator's criteria and evidence are, how
implement-feature fixes a finding or which tests it runs, what a stall is
and what happens on one, what makes a question material, when the run
commits, or what the run record holds. Those are compiled into run-pipeline and the built-in steps.

## What changed

| Rule | Where it lives |
|---|---|
| An author's deferral never excuses a criterion the work received: only a person's quoted words that name it and let it go waive one, never a go-ahead on an artifact listing it unmet. Each brief's out-of-scope row raises such a gap, and the panel's scope order points at the rule by name. | *What a fresh reviewer is given*; design-review and evaluator out-of-scope rows; mr-review-panel, standing order 3 |
| A fresh reviewer is told what the work received, not only the author's restatement: the design review's brief carries the ticket, each instruction a person gave the run and each answered question with its readings, quoted; the panel's brief carries the ticket or brief, with the spec labelled as the author's. | design-review, *What was asked*; mr-review-panel, *Assemble the brief* |
| A go-ahead approves the direction of what the person was shown, which stays its writer's; an answer binds the outcome of the reading it chose, not that option's mechanism, scope words or phrasing. "Must", "need", "never" or a plain statement of what is wanted binds; hedged words ("I think", "maybe", "should", "I'd like") and an option's words beyond its outcome set a default. Evidence against a default is never a blocking finding: where it changes an outcome the person names it is a question (an advisory written as one where the workflow takes no questions); otherwise the work follows the evidence and says so. | *What a fresh reviewer is given* |
| The evaluator's criteria include each answer with the reading it chose, and each assumption the plan, shape or spec labels, as the author's. Each criterion's evidence names the code that meets it and the test that pins it; one a test can pin that no test pins is an issue, blocking for a criterion the work received and advisory for the author's. | evaluator-spawn, *What was agreed* and step 5; run-pipeline passes the run's answers to nested workflows |
| An advisory the author leaves undone when its row ends is noted in that row by file and number. Once two fresh reviewers or evaluators of the run have raised it (the same defect at the same unit), it is a question for the person, asked once whatever materiality says: whether they want it. It joins the next park or goes on the MR, parks nothing by itself, and is neither declined again nor made blocking. | run-pipeline, **Questions** |
| A question is material only when a reading changes an outcome the ticket or a person names, or needs an `escalate` choice. Readings that differ otherwise (a unit, a stored record, a failure path) take the one the project's standards or nearest in-tree precedent follows, else the plainest, labelled as an assumption for a test to pin. | *Questions for a person* |
| A project step's body may name a later step, with no step producing `change` or `mr` up to it, at whose end or skip its questions park, so a run asks once and never writes code on an open question. | run-pipeline, **Questions** |
| No stall number. A check is stalled when the revision before it closed none of its findings, or when its file shows an earlier finding's defect (the same consequence) at another path, input or place (`recurs <n>`, a re-open included, the run saying why and counting doubt as a recurrence). The first stalled check parks the step at once, framing the decision: approve the author's stated removal, rule a finding not a defect, waive findings by name, or stop. *Loop bounds* names this park as the one exception to its re-open stop. `max-stalled-cycles` is gone (install and validate warn when a manifest still sets it); `max-cycles` (8) stays as a runaway guard. | run-pipeline, **Bound**; *Loop bounds*; `phases.yaml`; `glados.py` |
| A finding passed to implement-feature is a task covering its kind: list every place where the change has the same defect (not breaches that predate it), then fix each or name, per place, the input that shows it does not hold. | implement-feature, step 3 |
| implement-feature runs the tests of every area the diff touches and the unit suite; the full suite runs once per fix loop, in the evaluator, whose brief names the commands as CI runs them and the CI configuration, so a test job the brief leaves out is an issue. Committing code still needs the full suite, and the evaluator's run on the same diff counts. | implement-feature, step 5; evaluator-spawn, *How to verify* and step 3; *Git conventions* |
| The record is an index: under its header, `## Now` (the step in progress, what it waits on, the next action), kept current; a reader reads it and the rows its step needs. Findings stay in their check's files, and how a revision answered them in `<record>.<id>.revision-<n>.md`, which no brief names, so the author's dispositions never reach the next reviewer through the artifact. | run-pipeline, step 3 |
| A row's process files go in one commit when the row ends or parks, never file by file; a pipeline with no branch of its own makes no row commit until it parks and cuts one, so one that ends without parking commits only the epilogue's record. | run-pipeline, **Commits** and **Branch** |

To keep run-pipeline from growing, rules it stated twice now live once:
a nested escalation ending the run (under the modifiers), the parked run's
claim, work-unit row and pending items (the epilogue, now worded for any
park), the push after the record and the work left for a human with no MR
(under **Branch**), the pending MR items open-mr posts (the epilogue),
self-review's verdict timing and its branch freeze (**After the MR
opens**), the canon consult point (*Consulting canon*), a design review's
"never a verdict", which the post-MR rule contradicted, the standards
gate's bound stop (*Loop bounds*, in every core that carries the gate), the
shape's decision split (its own table), and the build-feature bypass note
(the pipelines guide).

## Left to projects

These are expressible in a project's own step bodies, `glados.yaml` and
standards, and are being tried there first:

- **Outcome coverage and answer trace at the gates** (the design audit and
  the defense): mapping each outcome in the ticket's and the person's own
  words, and each answer, to the plan unit, code and test that meet it. Core
  now gives every fresh reviewer what the work received, makes the author's
  deferral of such an outcome a finding, and makes an answer or labelled
  assumption with no pinning test an evaluator issue; the per-gate tables
  are project text.
- **Whether verify-feature's evaluator loop parks inside a pipeline.** A
  re-open there still ends the run with an escalation, which reaches a
  person with the cycle history; making it park needs a park in
  verify-feature, which no trial run has called for yet.
- **Plain-first as "the plainest design that meets every outcome"**, with
  growth that meets an outcome expected and growth with none the finding.
  Core has no plain-design step to redefine.
- **A flag threaded through many signatures is a structural finding** that
  names the one place that could own the decision. A project's reviewing
  standard reaches every gate and the MR panel.
- **Two kinds of design finding**, decision or structure fixed in design and
  path detail carried into the spec as a named test obligation. The two
  tiers carry it: a project gate can write a path-detail finding as an
  advisory obligation that a later project gate checks. Core's part is the
  labelled assumption a test pins.
- **Eliminate before enumerating** a class of edges (idempotent steps, one
  owner for the state, the framework's retry). This is how a project's
  design steps tabulate.
- **A growth check on units added after the design audit** (by the spec or
  the implementation). The evaluator already lists every public unit the
  diff adds beyond the shape and reviews it on its merits; a project that
  wants the growth question asked at spec time adds a gate there.

## v3.1: informed input

After the third run, the owner of GLaDOS: "Humans use imprecise language
and machines tend to assume they meant exactly what they said. This needs
to be challenged, particularly if the evidence in the code points another
direction." And, since he tends to take the recommended option without the
context to judge it: "We need to find a way to have informed human input,
not just snap answers to questions that we waited 2 hours for."

| Rule | Where it lives |
|---|---|
| Each clause of a quote takes the commitment tag its own words give, until the person corrects it: a *Directive* binds; a *Preference*, a hedged want ("I think we need") included, is a default evidence may override; a *Hunch*, a belief about what is true, is a hypothesis tested against the code that stands unless contradicted; an *Assent* approves only the direction of what was shown and reopens on material evidence that was not, which the reopened question names. A brief quotes people's words untagged. It replaces v3's "words bind as firmly as they were said". | *What a fresh reviewer is given* |
| Evidence outside the change against a person's words is written as "your words say X (tag); the code shows Y; I propose Z", naming where: a question against a Directive (which stands meanwhile) or where material, else the work follows Z. Neither raising one nor following one past a Preference or Hunch blocks; any other departure, one under a tag softer than the words included, breaks a criterion the work received, so a change that does not do what the words say is never recast as a challenge. The design reviewer checks each tag, challenge and question (its form and door) and looks for words used untagged or departed from unstated; the pooled `decision` outcome lists each challenge the work followed; a nested built-in stage is passed the tags. | *What a fresh reviewer is given*; design review, item 7; run-pipeline, **Nested workflows** and step 5 |
| A question reaches a person only complete and specific to it: the decision in one line, a scenario today and under each reading, each reading's effect on users, cost and risk, the door and what makes it one-way, the finder's recommendation with its confidence, evidence a reader can open (a file and line, test, data or quote) and what favours it over each other reading, and what happens if no one answers. A stall's park carries the parts that fit a choice among findings: a scenario, each option's cost and risk, and the author's recommendation with its confidence and evidence. | *Questions for a person*; run-pipeline, **Bound** |
| A question is a one-way door when one reading needs an `escalate` choice or leaves an outcome the ticket or a person names unmet, or the readings differ in what users see of one; when unsure, one-way, and an author answering one has assumed the answer. A one-way door parks. Any other is a two-way door: the author answers it by its finder's recommendation, except that a person's Directive or chosen reading stands; the pooled `decision` outcome lists it and it joins the next park or the MR for the person to confirm or overturn; unanswered, the answer stands, and one overturned is revised in each artifact it reached. A twice-declined advisory carries its reviewers' findings as its recommendation beside the author's reasons, and is routed by its door, the work unchanged until the person answers. | *Questions for a person*; run-pipeline, **Questions** and step 5 |

Where the items meet: a plain statement of what is wanted stays a
Directive, so the ticket's outcomes keep binding, and a hedge before a want
leaves a Preference, never a Hunch the code could "disprove"; overriding a
softer tag where that is a one-way door still parks first. The spec's
schema, public API and data doors are the project's `decisions:` classes
for those choices, not a second list in core: a reading that needs one
classed `escalate` is a one-way door, and one the phase classes `agent` or
`record` is decided and recorded as *Decision rights* already has it, a
table this branch adds staying one decision until it reaches the target.
So *Decision rights* is unchanged, and a stored record is again a
difference that takes the plainest reading unless it changes a named
outcome. Only a person's answers reach a design reviewer as criteria the
work received.

**Run 3's parks.** The four narrow ones (a failure inside a failure path, a
deploy window, two defense-time variants of the same kind) were already
labelled assumptions under v3, and are two-way doors besides. The two
decision-level answers that kept a worked-out value on a retry or a
fallback are two-way doors unless a reading leaves a named outcome unmet or
changes what users see of one, which each brief's door must now say. The
availability-against-data-quality choice changes an outcome users see that
the ticket names, so it still parks, now with a scenario and a
recommendation.
