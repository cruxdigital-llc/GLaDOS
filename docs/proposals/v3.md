# Healthier, not just smaller

> Design rationale for the third round of 2.5 changes to run-pipeline and
> the fresh reviewers around it. The rules are in
> `src/vocabulary/review-inputs.md`, `src/vocabulary/questions.md`,
> `src/workflows/run-pipeline.md` (step 3 and **Branch**, **Commits**,
> **Bound** and **Questions** in step 4), `src/vocabulary/design-review.md`,
> `src/vocabulary/loop-bounds.md`, `src/workflows/implement-feature.md`,
> `src/modules/evaluator-spawn.md`, `src/modules/mr-review-panel.md`,
> `src/vocabulary/git-conventions.md` and, from v3.2,
> `src/vocabulary/person-words.md`, `src/vocabulary/mr-notes.md`,
> `src/kernel/epilogue.md` (step 4, the run ledger) and the `ledger`
> command in `bin/glados.py`.
> Follows [design-loop.md](design-loop.md) and
> [review-inputs.md](review-inputs.md).

**Status:** shipped in 2.5.0. **Baseline:** the 2.5.0 candidate with
*Questions for a person* and the cycle table.

## The problem

The objective is a healthier change: every outcome the ticket and the
person ask for met robustly, with a structure the next caller can build on,
leaving the code it touches better. Plainness is a constraint on how it gets
there, not the goal. Three trial runs of a plain-first project pipeline on
one ticket, and a blind comparison of the third run's change with two other
implementations of the same ticket, showed the 2.5 loop drifting toward the
smallest change instead.

- **Outcomes were checked in the author's words.** The gates verified the
  author's restated outcomes and passed. Blind reviewers read the ticket's
  own words and found two of its four outcomes only partly met. Nothing in
  core stopped an author's "deferred" or "not met" from excusing an outcome
  the ticket asked for.
- **An answer was not carried out.** A person chose a reading that asked for
  certain cases to be reported; the change never reported them, and no gate
  asked where the answer was implemented or tested.
- **A repeated advisory never bound.** Three independent checks raised the
  same missing clean-up of stored rows as advisory; the author declined it
  each time, and the blind reviewers found it again.
- **The loop still turned on numbers.** A stalled-cycle bound of 3 was
  arbitrary, and a cycle that patched one path of a recurring class counted
  as progress. Narrow failure-path variants each parked the whole run for a
  person, because any reading that changed a unit or a failure path was
  "material".
- **Hedged words were read as hard requirements.** "I think I'd like…"
  cost one run three failed design reviews, and a later gate blocked twice
  on the detail of an option's wording that the person had only assented
  to.
- **Process weight.** The run record reached 182 KB and every agent read it
  whole. Each fix loop ran the full suite twice (implement-feature's step 5
  and the evaluator), about an hour each on the trial machine. The run made
  25 process commits beside 6 product commits, 6 of them for briefs alone.

## Why core, not project

A project chooses its steps, gates, checkpoints and the numbers in
`params.pipeline`, and its step bodies say what each gate checks. It cannot
change what a fresh reviewer is given or told a deferral excuses (that
fragment is compiled into the evaluator, the MR panel and every design
review), what the evaluator's criteria and evidence are, how
implement-feature fixes a finding or which tests it runs, what a stall is
and what happens on one, what makes a question material, when the run
commits, or what the run record holds. Those are compiled into run-pipeline and the built-in steps.

## What changed

| Rule | Where it lives |
|---|---|
| An author's deferral never excuses a criterion the work received: only a person's quoted words that name it and let it go waive one, never a go-ahead on an artifact listing it unmet. | A fresh reviewer is told what the work received, not only the author's restatement: the design review's brief carries the ticket, each instruction a person gave the run and each answered question with its readings, quoted; the panel's brief carries the ticket or brief, with the spec labelled as the author's. | design-review, *What was asked*; mr-review-panel, *Assemble the brief* |
| A go-ahead approves the direction of what the person was shown, which stays its writer's; an answer binds the outcome of the reading it chose, not that option's mechanism, scope words or phrasing. "Must", "need", "never" or a plain statement of what is wanted binds; hedged words ("I think", "maybe", "should", "I'd like") and an option's words beyond its outcome set a default. Evidence against a default is never a blocking finding: where it changes an outcome the person names it is a question (an advisory written as one where the workflow takes no questions); otherwise the work follows the evidence and says so. | *What a fresh reviewer is given* |
| The evaluator's criteria include each answer with the reading it chose, and each assumption the plan, shape or spec labels, as the author's. Each criterion's evidence names the code that meets it and the test that pins it; one a test can pin that no test pins is an issue, blocking for a criterion the work received and advisory for the author's. | evaluator-spawn, *What was agreed* and step 5; run-pipeline passes the run's answers to nested workflows |
| An advisory the author leaves undone when its row ends is noted in that row by file and number. Once two fresh reviewers or evaluators of the run have raised it (the same defect at the same unit), it is a question for the person, asked once whatever materiality says: whether they want it. | A finding passed to implement-feature is a task covering its kind: list every place where the change has the same defect (not breaches that predate it), then fix each or name, per place, the input that shows it does not hold. | implement-feature, step 3 |

Committing code still needs the full suite, and the evaluator's run on the same diff counts. | implement-feature, step 5; evaluator-spawn, *How to verify* and step 3; *Git conventions* |
| The record is an index: under its header, `## Now` (the step in progress, what it waits on, the next action), kept current; a reader reads it and the rows its step needs. Findings stay in their check's files, and how a revision answered them in `<record>.<id>.revision-<n>.md`, which no brief names, so the author's dispositions never reach the next reviewer through the artifact. | run-pipeline, step 3 |
| A row's process files go in one commit when the row ends or parks, never file by file; a pipeline with no branch of its own makes no row commit until it parks and cuts one, so one that ends without parking commits only the epilogue's record. (Superseded in v3.2, *Records on the ledger*: these are now `ledger save`s to `glados/ledger`, never commits on the work branch.) | run-pipeline, **Commits** and **Branch** |

To keep run-pipeline from growing, rules it stated twice now live once:
a nested escalation ending the run (under the modifiers), the parked run's
claim, work-unit row and pending items (the epilogue, now worded for any
park), the push after the record and the work left for a human with no MR
(under **Branch**), the pending MR items open-mr posts (the epilogue),
self-review's verdict timing and its branch freeze (**After the MR
opens**), the canon consult point (*Consulting canon*), a design review's
"never a verdict", which the post-MR rule contradicted, the standards
gate's bound stop (*Loop bounds*, in every core that carries the gate), the
shape's decision split (its own table), and the build-feature bypass note
(the pipelines guide).

## Left to projects

These are expressible in a project's own step bodies, `glados.yaml` and
standards, and are being tried there first:

- **Outcome coverage and answer trace at the gates** (the design audit and
  the defense): mapping each outcome in the ticket's and the person's own
  words, and each answer, to the plan unit, code and test that meet it. Core
  now gives every fresh reviewer what the work received, makes the author's
  deferral of such an outcome a finding, and makes an answer or labelled
  assumption with no pinning test an evaluator issue; the per-gate tables
  are project text.
- **Whether verify-feature's evaluator loop parks inside a pipeline.** A
  re-open there still ends the run with an escalation, which reaches a
  person with the cycle history; making it park needs a park in
  verify-feature, which no trial run has called for yet.
- **Plain-first as "the plainest design that meets every outcome"**, with
  growth that meets an outcome expected and growth with none the finding.
  Core has no plain-design step to redefine.
- **A flag threaded through many signatures is a structural finding** that
  names the one place that could own the decision. A project's reviewing
  standard reaches every gate and the MR panel.
- **Two kinds of design finding**, decision or structure fixed in design and
  path detail carried into the spec as a named test obligation. The two
  tiers carry it: a project gate can write a path-detail finding as an
  advisory obligation that a later project gate checks. Core's part is the
  labelled assumption a test pins.
- **Eliminate before enumerating** a class of edges (idempotent steps, one
  owner for the state, the framework's retry). This is how a project's
  design steps tabulate.
- **A growth check on units added after the design audit** (by the spec or
  the implementation). The evaluator already lists every public unit the
  diff adds beyond the shape and reviews it on its merits; a project that
  wants the growth question asked at spec time adds a gate there.

## v3.1: informed input

After the third run, the owner of GLaDOS: "Humans use imprecise language
and machines tend to assume they meant exactly what they said. This needs
to be challenged, particularly if the evidence in the code points another
direction." And, since he tends to take the recommended option without the
context to judge it: "We need to find a way to have informed human input,
not just snap answers to questions that we waited 2 hours for."

| Rule | Where it lives |
|---|---|
| Each clause of a quote takes the commitment tag its own words give, until the person corrects it: a *Directive* binds; a *Preference*, a hedged want ("I think we need") included, is a default evidence may override; a *Hunch*, a belief about what is true, is a hypothesis tested against the code that stands unless contradicted; an *Assent* approves only the direction of what was shown and reopens on material evidence that was not, which the reopened question names. A brief quotes people's words untagged. It replaces v3's "words bind as firmly as they were said". | *What a fresh reviewer is given* |
| Evidence outside the change against a person's words is written as "your words say X (tag); the code shows Y; I propose Z", naming where: a question against a Directive (which stands meanwhile) or where material, else the work follows Z. Neither raising one nor following one past a Preference or Hunch blocks; any other departure, one under a tag softer than the words included, breaks a criterion the work received, so a change that does not do what the words say is never recast as a challenge. The design reviewer checks each tag, challenge and question (its form and door) and looks for words used untagged or departed from unstated; the pooled `decision` outcome lists each challenge the work followed; a nested built-in stage is passed the tags. | *What a fresh reviewer is given*; design review, item 7; run-pipeline, **Nested workflows** and step 5 |
| A question reaches a person only complete and specific to it: the decision in one line, a scenario today and under each reading, each reading's effect on users, cost and risk, the door and what makes it one-way, the finder's recommendation with its confidence, evidence a reader can open (a file and line, test, data or quote) and what favours it over each other reading, and what happens if no one answers. A stall's park carries the parts that fit a choice among findings: a scenario, each option's cost and risk, and the author's recommendation with its confidence and evidence. | *Questions for a person*; run-pipeline, **Bound** |
| A question is a one-way door when one reading needs an `escalate` choice or leaves an outcome the ticket or a person names unmet, or the readings differ in what users see of one; when unsure, one-way, and an author answering one has assumed the answer. A one-way door parks. Any other is a two-way door: the author answers it by its finder's recommendation, except that a person's Directive or chosen reading stands; the pooled `decision` outcome lists it and it joins the next park or the MR for the person to confirm or overturn; unanswered, the answer stands, and one overturned is revised in each artifact it reached. A twice-declined advisory carries its reviewers' findings as its recommendation beside the author's reasons, and is routed by its door, the work unchanged until the person answers. | *Questions for a person*; run-pipeline, **Questions** and step 5 |

Where the items meet: a plain statement of what is wanted stays a
Directive, so the ticket's outcomes keep binding, and a hedge before a want
leaves a Preference, never a Hunch the code could "disprove"; overriding a
softer tag where that is a one-way door still parks first. The spec's
schema, public API and data doors are the project's `decisions:` classes
for those choices, not a second list in core: a reading that needs one
classed `escalate` is a one-way door, and one the phase classes `agent` or
`record` is decided and recorded as *Decision rights* already has it, a
table this branch adds staying one decision until it reaches the target.
So *Decision rights* is unchanged, and a stored record is again a
difference that takes the plainest reading unless it changes a named
outcome. Only a person's answers reach a design reviewer as criteria the
work received.

**Run 3's parks.** The four narrow ones (a failure inside a failure path, a
deploy window, two defense-time variants of the same kind) were already
labelled assumptions under v3, and are two-way doors besides. The two
decision-level answers that kept a worked-out value on a retry or a
fallback are two-way doors unless a reading leaves a named outcome unmet or
changes what users see of one, which each brief's door must now say. The
availability-against-data-quality choice changes an outcome users see that
the ticket names, so it still parks, now with a scenario and a
recommendation.

**Measured.** Compiled `run-pipeline.md`: 11,799 words before, 12,148
after (+2.96%). v3.1 is held to the +3% its operator set rather than v3's
net-neutral rule, since it adds rules where v3 moved them. `questions.md`
with `review-inputs.md`: 627 before, 862 after (+37%). Each other core
carrying *What a fresh reviewer is given* grows 124 words. Tests: 258
before, 262 after.

**Left to projects.** Refactor pressure (how much refactoring each touched
unit already needs and how much the change adds, ranked against the
repository's own distribution) starts in a project's facts script and
design steps, and tagging in the research step that first gathers people's
words.

## v3.2: people on the MR, and doors that route

**Evidence.** After the third run's MR passed its panel (eight approvals,
no blocking finding), a human reviewer posted a review: approve, two gaps
the MR did not list, seven advisories, and a note that one two-way answer
still needed the owner's confirmation. The run recorded "No document of
this run routes a person's MR note", and nothing answered it. On the
attempt before, every GLaDOS gate approved and the same reviewer found
four blocking issues. GLaDOS posts under a person's account, so the
account a note came from cannot tell the two apart. The run's commit
messages also broke the project's 80-column rule, which a commit-msg hook
and a CI job enforce: the clones never installed the hook, and CI went red
after the push, when a message costs a rewrite to fix. An independent
adversarial check of v3.1 upheld three findings against core (a person's
overturn or instruction posted on the MR has no reader; the panel's brief
leaves out the answers a person gave, so the panel can block on a choice a
person already made; a person's review never enters the loop) and found a
fourth plausible (a twice-raised advisory defaults to the declined state).
Three blind classifiers applied v3.1's door rule to the third run's nine
questions: they agreed with each other on all nine, every one one-way,
where the rule's author expected four, and reported some thirty
ambiguities between them. A worked demonstration rewrote two of the run's
questions in v3.1's Form and recorded where it was hard to fill, redundant
or long.

| Rule | Where it lives |
|---|---|
| A person's note on the MR is input to the review loop. Everything a run posts on an MR, in any step, starts with `(GLaDOS <workflow>)`, whatever the sink config. A note or reply whose first line does not start with it (a quote of a GLaDOS note does not) is a person's when someone with a role on the project wrote it, whichever account posted it, unless they wrote the change: the marker tells GLaDOS from the person whose account it posts under, and does not make every unmarked comment a person's. GLaDOS wrote a change its runs made, whatever name its commits and MR carry, so where the agents work under the owner's account, the owner reviewing their change is a person, which is the case this rule exists for. A system note or a bot's is no one's, and anyone else's, such as a passer-by on a public repository, is evidence. Every kind of note the platform keeps is read: on GitHub, comments, reviews with their state, and inline review comments are three lists. Each pass quotes, by id, each person's note no earlier pass quoted, and lists them again before it decides, so a review posted while a pass runs is read. An instruction or answer is a criterion the work received, and each point a finding labelled as theirs, at the tier they give it whatever the scale says, so a review that says nothing blocks blocks nothing; with no tier given, a Directive or chosen reading the change does not meet is blocking, and any other point takes the scale's tier. A point is open until the change meets it or the author answers it on the MR in the *Challenge in the open* form; against a blocking one that answer is a question for that person, and it closes only when the change meets it or they withdraw or waive it in their own words, never by a panel's approval, a refuter or the author's reasons. A point asking someone other than the author (a confirmation, a reopened answer) closes only when they answer. A person's point no review-mr run has quoted starts a new round of review cycles, so a review posted after the loop used its cycles is still taken through it: the bound counts cycles per round, while the cycle number runs on, so the next pass still names the findings left open and their disposition; on an unchanged head it goes straight to address-review, quoted with its id, whatever the last pass decided, so the pass after the fix does not start a second round for it. address-review's bound check counts from the round review-mr's record notes. Whether the loop runs again is said once, in address-review's handoff: a fix pass that commits nothing ends it. A verdict comment leads with the verdict, after the marker. | *People on the merge request* (`mr-notes.md`, in review-mr and address-review); epilogue, step 5; *Publishing a verdict*; review-mr steps 2, 4 and 8; address-review steps 1 and 7; *Loop bounds* |
| The tags and the challenge form are their own fragment, *A person's words*, which *What a fresh reviewer is given* includes, so address-review carries them without the brief rules. | `person-words.md`; `review-inputs.md` |
| The panel is given what the work received as the design reviewer is: the ticket or brief, each question a person answered in the run that opened the MR with its readings and answer, and each instruction or answer people gave on the MR, quoted. The panel's list names the MR description too, and review-mr gathers from that list instead of keeping a second one. | mr-review-panel, *Assemble the brief*; review-mr step 4 |
| A question's default is the reading a person's Directive or chosen reading takes, else its finder's recommendation. Only a person answers a one-way door: one with no default (people's words take two readings), or whose default needs an `escalate` choice or leaves unmet an outcome another reading meets. A two-way door is answered by its default. Readings differ materially when they differ in whether a named outcome is met, each outcome counted as fully as any reading reads it, less what a person's words let go; when unsure, they do. What users see no longer routes a question. | *Questions for a person*; run-pipeline, **Questions** |
| A twice-declined advisory is asked with its two findings quoted as its words and recommendation, so *Doors* makes their recommendation its default unless a person's Directive or chosen reading takes another, and the work takes it unless its door is one-way. It is still never blocking. | run-pipeline, **Questions** |
| A one-way question a step after open-mr posts on the MR goes to review-mr with that step's blocking findings, and stays open, keeping the MR from review-clean, until a person answers it there. A pass the panel approves leaves the MR waiting on that person, not review-clean. | run-pipeline, step 5; review-mr steps 4 and 8 |
| An unhedged claim, a stated problem included, is a Hunch the artifact tests; a problem a ticket or brief states also asks for its absence, as a Directive. A reviewer's stated problem does not, or every advisory written as a problem would bind. Choosing an option is Assent however the option is worded. | *A person's words* |
| The Form runs in the order a person answers from: the decision, a scenario through today's code, the readings with what users would see in that scenario, their cost, risk and reversibility, the recommendation with what fact would change it, the door and its default, then the words, a tested Hunch with what the code showed and a reopened Assent with what its giver was not shown. "What happens if no one answers" is gone: the door and default say it. | *Questions for a person*, **Form** |
| Install any commit-msg hook the project declares before the first commit. Agents usually work in fresh clones, which carry no hooks, so this is core rather than one operator's harness. | *Git conventions* |

**Why the door changed.** v3.1 made a question one-way when one reading
left a named outcome unmet or the readings differed in what users see. A
reading that changes a named outcome nearly always leaves it unmet on some
path, so the test all but coincided with materiality, and every question
parked, the narrow ones v3.1 meant to be two-way included. The
classifiers also could not say from whose reading "unmet" is judged when
the readings are rival meanings of the outcome's own words; the rule fired
on an outcome unmet under every reading; "users" was undefined; and two of
one person's choices that conflicted had no route. What matters is who
may give up part of what a person asked for. Deciding a reading that meets
every outcome as fully as any reading does gives nothing up, so the run
takes it and the person may overturn it on the MR, which now has a reader.
Deciding one that leaves unmet an outcome another reading meets is a
waiver, which only the person gives: v3's waiver rule, applied to
questions. Cost, risk and reversibility stay in the Form for the person to
weigh, and the choices a team cannot take back stay the project's
`escalate` classes rather than a second list in core.

Applied to the nine: two of one person's earlier choices take different
readings of one question, and a stated problem's absence and a chosen
reading take different readings of another, so those two have no default
and park. The other seven take the reading the people's words take (a
Directive at its fullest, a chosen reading, or an earlier answer less what
it let go), which meets every outcome, so they are two-way. Two parks
where the run made six, as v3.1 read literally would have too.

**Declined.**

- Routing by reversibility or price, which the classifiers proposed. Both
  are judgements the person weighs from the Form; routing on them would
  bring back a tuned threshold.
- A rule that old code running during a rollout is not the change's. A
  mixed-version deploy can do real harm, so a rollout question is routed
  like any other.
- A rule merging duplicate questions and settling follow-ups. An earlier
  answer that takes a reading of a later question is that question's
  default, and *Assent* already says only evidence its giver was not shown
  reopens it; a duplicate that does not park costs a line in the pooled
  `decision`.
- Making a stored record material again. A reading that needs a schema
  change is an `escalate` choice where the project classes it so, and the
  preamble already makes reworking a table the branch adds part of one
  decision.
- That a question routed to the MR stays open until a person answers. It
  would make every two-way door a merge blocker; the overturn now has a
  reader instead.
- From the Form demonstration, "the first four enough to answer it" and
  "once built": the order already says the first, and the scenario the
  second.

### Records on the ledger

**Evidence.** The third run committed its record and step artifacts to the
feature branch: 63 files under `.glados/runs/` (research, plan, shape,
tables, spec, review briefs and reviews, evaluation briefs and
evaluations), many over 1,000 lines, so its MR showed 112 changed files,
most of them process records. The person who owns GLaDOS, looking at that
MR: "The run record is a stupid amount of diff to add." The epilogue
committed every run's record to the working branch, except review-mr's and
address-review's, which went to `glados/ledger`, and run-pipeline committed
each step's artifacts with the step.

| Rule | Where it lives |
|---|---|
| Every run's record and step artifacts live on the `glados/ledger` branch, never on a work branch: the MR carries the change and the comment, and the ledger carries the trail. review-mr's and address-review's rule became the general one, said once. Agents still read and write them in `.glados/runs/`, which the clone's git exclude file keeps out of every branch's commits: install, migrate, `ledger save` and `ledger restore` add `/.glados/runs/*` to it. A project in a subdirectory of its repository (a monorepo package) keeps its own `.glados/runs/`: its line is `/<dir>/.glados/runs/*`, and its records go on the ledger under `<dir>/.glados/runs/`, so two projects in one repository never share one. | epilogue, step 4; `ledger`, `install`, `migrate` |
| `.glados/glados.py ledger save` is the one way records get there, at every point the run committed them before: a row's end or park, open-mr, the epilogue, and again for any record update made while publishing. A failed push says to note it in the record, and the next save retries it. | epilogue, step 4; run-pipeline, **Commits**; open-mr; `ledger save` |
| Every run starts with `ledger restore`, which copies the ledger's records into `.glados/runs/`, so prior records (preamble step 4) and a park resumed in another session or on another machine are read from there. | preamble, step 1; run-pipeline step 1 |
| A record or artifact is linked by its ledger copy (`ledger link <path>`), never by a work-branch path: in the MR description, the outcomes and an escalation. | epilogue, step 4 |

**The mechanism.** `ledger save` builds its commit in a temporary index from
the ledger's own tree, so the checked-out branch, the index and every
tracked file stay as they are, moves `refs/heads/glados/ledger` with a
compare-and-swap, and pushes it. It never force-pushes. A missing branch is
created as an orphan holding only `.glados/runs/`; a ledger that already
exists, such as one cut from the main line, is built on as it is. With no
paths it saves every file under `.glados/runs/` that is new or changed,
leaving out the markers, any ignore file there and the files the branch
tracks unchanged; a named path that no longer exists is removed from the ledger,
which is how steward compacts. When another session pushed meanwhile, the
save fetches, and if the push is still rejected, or the remote lost the
ref's lock to a push that landed after it advertised its refs, it fetches,
merges and pushes again, up to five times. The other session's commit becomes a
parent, so neither side's history is lost: a file one side changed takes
that side, and a file both changed is merged keeping both sides' lines
(`git merge-file --union`), written back to the working copy, with a
warning naming it. Each working tree keeps, in its git directory, the
version of each file it last synced with the ledger: that is the base the
merge compares against, and it tells a stale copy from an edited one. A
copy equal to that version, or, for a path this tree never synced, to one
the ledger held before, is refreshed and never written back over it; any
other difference is an edit, a text put back as it was before included.
`restore` never overwrites a copy with changes the ledger lacks, or a file
the branch tracks, and removes a synced copy of a file the ledger has
removed, so a record steward compacted in one clone is not read or
compacted again in another. A push that fails for any other
reason (a protected branch, no network) keeps the commit, exits 1 and says
so; the next save pushes it. A ledger checked out in a worktree is refused,
since moving the branch under that checkout would show the save there as
an undone change.

**Where the project's own rows go.** The `SPEC_LOG.md` work-unit row stays
with the work on the working branch. It says the unit is done, so it must
reach the target branch when, and only when, the change merges (a closed MR
must not log its unit done), and SDA tooling reads it there; it is one row,
which a reviewer reads as the unit's summary, linking the record on the
ledger. `claims.md` stays at the repo root on the working branch, the
location SDA's profile and its boards read. On a merged MR it adds the claim
and its release, two lines. A claim on a work branch is seen only by runs
on that branch, which the ledger would fix, but moving it there changes
SDA's file locations and needs a merge rule for concurrent appends, so it
is left for its own change. review-mr and address-review add neither: an
MR's unit is its opener's, a GLaDOS opener's row is already on the branch,
and a person's MR is not a GLaDOS unit. Before, a standalone address-review
run committed a row to the MR's branch each time it ran, a second row for
one unit and process in the diff the owner wanted kept to the change.

**Migration.** Nothing is migrated or rewritten. Records a branch already
carries stay there as history: a save does not copy them, a restore does not
overwrite them, steward leaves them, and the hooks look only at the runs in
flight. Nothing is committed to keep records out of a branch: install,
migrate (which converts old history into records) and the `ledger restore`
every run starts with put the line in the clone's exclude file before the
clone has a record, so committing `.glados/` after either takes none.

**Declined.** A line in the project's root `.gitignore` (an edit to a file
the project owns), and an ignore file in `.glados/runs/`, which the first
build used: a branch that tracks it and one that lacks it make a checkout
either abort over an untracked copy or delete it, leaving every record open
to `git add -A`. The exclude file does not travel, but no clone has a
record before install, migrate or the `ledger restore` its first run
starts with writes the line. A worktree checked out on the ledger, which
operators improvised: it leaves an agent to copy, add, commit, pull and
push by hand at every save, the prose the helper replaces.

## Known gaps at 2.5.0

Each is rare and fails closed or is a matter of wording; none is a crash, a
guard that lets a session end without a saved record, or a record lost on
the path a team normally takes.

- **Hook interpreter.** The documented hook commands, and the
  `.agents/hooks.json` install writes, call `python`. Where only `python3`
  exists (stock macOS; Debian and Ubuntu without `python-is-python3`) the
  hook cannot start, which Claude Code and Gemini CLI treat as a
  non-blocking error, so the guard does not run. Every getting-started page
  and `hooks/README.md` say to write `python3` there; no one command name
  works on every platform's stock Python. A `doctor` warning when the wired
  interpreter is missing would close most of it.
- **Names that differ only in case** (Windows, macOS). Linux, or a
  mis-cased explicit path on macOS, can put `R1.md` and `r1.md` both on the
  ledger; a restore on a case-insensitive file system writes both into one
  file. GLaDOS's own naming never makes two.
- **A ledger name a clone cannot hold** (Windows-reserved characters, a
  trailing period or a device name; a name that is not UTF-8 on Windows or
  macOS; a path past the file system's limit) stays on the ledger with a
  note and is not restored in that clone.
- **Links under `.glados/runs/`** are never saved. A record that is a link
  blocks the guards; a step artifact linked to a directory counts as no
  file.
- **A repository kept under a run's artifacts** is left off the ledger with
  a note, and the guards block on its files until it is moved.
- **git's "dubious ownership" refusal** makes `ledger save` report that the
  directory is not in a git repository, without git's own message naming
  the fix.
- **`effective-config --ref`** against a branch that still has 2.4's preset
  table lists the missing keys without the line saying the reinstall
  supplies them.
- **A project in a subdirectory of its repository:** CI enforcement is not
  supported (install and doctor say so); doctor checks a CODEOWNERS file
  the platforms do not read there; the kernel text and older profiles still
  say `claims.md` is at the repository root, where install puts it in the
  project.
- **A no-op `ledger save`** can leave the clone's `glados/ledger` behind the
  remote's while printing the remote's tip; nothing is lost.
- **The test suite needs Python 3.11+** (`tomllib`); the tool itself runs
  on 3.10, covered by a smoke test.
- **Not run here:** macOS, and the GitLab job override in a real GitLab
  pipeline.
